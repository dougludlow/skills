# Orchestrate

Own orchestration from the agreed outcome through verified acceptance: decompose the effort, dispatch workers, manage dependencies, and integrate their results. The human uses this chat to steer the project and review meaningful milestones. Workers own bounded execution; keep this chat focused on direction, dependency decisions, acceptance, and the next useful action. Worker completion alone does not establish project completion.

Write worker briefs, reports, project records, and heartbeat prompts in ordinary English. Use complete sentences with normal spacing; shorten by removing repetition and linking detail. Use familiar technical terms and explain project-specific shorthand on first use. Keep exact IDs, hashes, commands, and measurements in labeled fields or supporting evidence so they remain available without carrying the explanation.

## Establish or recover the project

Recover from current human instructions and the record's current overview and [resume state](references/orchestration-record.md#resume-state): acceptance criteria, constraints and permissions, active assignments and artifact versions, wait cursors, monitoring owners, and next actions. Reconcile fresh compact worker and artifact status before dispatching. Read bounded chat history or detailed evidence when that current context is missing, changed, conflicting, or insufficient for the decision. Reuse existing work and permissions. Reload guidance when it has changed or is unavailable after compaction; otherwise retain it in working context and read reference sections only as needed.

On initial setup or when the title or pinned placement needs correction, [name and pin this orchestrator chat](references/codex-orchestration.md#name-and-pin-the-orchestrator) using the orchestrator naming convention. Reuse a suitable project name on resume and honor explicit human naming instructions.

Create a compact project record using [references/orchestration-record.md](references/orchestration-record.md). Prefer an existing suitable record; otherwise save a local task artifact and report its path. Follow documentation rules when placing it inside a repository, and keep operational notes out of deliverable commits unless requested. Record:

- Desired outcome, why it matters, observable acceptance criteria, and scope boundaries.
- For an experiment: question, baseline/comparison, useful result, and stopping condition. A supported negative finding can complete an experiment.
- Reviewable milestones and the next human review point.
- Work units, dependencies, owners, chat IDs, workspace/branch, artifacts, and evidence.
- Material decisions and permissions, including where the human gave them.

Keep the active goal, current milestone, accepted constraints, and next decision in working context. Update the record after material changes; use it to recover after compaction or in later sessions. Keep the readable current overview and resume state together at the top, assessed from reconciled evidence. Move completed assignments and superseded status below the current sections or into linked history, retaining their evidence and provenance. Link detailed evidence instead of copying transcripts or sensitive data.

Linear projects and Codex workspace projects are separate concepts. A Linear issue is an optional work-unit link: one issue can need several workers and one work unit can cover several issues. Local experiments need neither projects nor tickets in Linear. Use existing trackers where useful; create or alter tracker structure only within the user's request. For Swell Linear, use MCP exclusively.

## Set the working agreement

Usually start from planning already done: recover and operationalize the agreed plan instead of restarting discovery. If planning is incomplete, use judgment to fill the gaps needed for the next useful milestone; involve the human for consequential choices. Infer defaults from the conversation and established user instructions. Ask only for consequential missing choices. Explain the outcome, initial milestones, next review point, and material uncertainty. If the user requests approval before execution, hold dependent execution until approved; otherwise progress within the authorized scope.

When the human explicitly invokes this skill, start orchestrating the requested effort as soon as enough context is available. Treat that invocation as authorization for routine project execution through subagents, isolated worktrees, and reviewable artifacts within the requested scope. Do not add a generic planning or delegation approval gate. Ask only when consequential information, context, or guidance is missing, or an action requires separate authorization under current tool rules or the human's constraints. Automatic skill loading alone is not an execution request.

Record the orchestration authority and its human source, including creating/managing visible worker chats, messaging the defined managed chats, publishing artifacts, and any requested monitoring or cleanup. Carry granted permission forward rather than asking for each worker. Follow current tool rules for visible chats and messages. Routine orchestration authority does not authorize marking PRs ready, merging, deploying, production changes, or contacting people.

Default to human review at meaningful milestones and material decisions, while continuing independent authorized work. Review sooner when evidence changes the approach, scope or operational risk grows, a major design choice remains, or an irreversible action requires approval. Bring a recommendation and concrete result or prepared action. Preserve the user's draft-PR and other approval boundaries.

## Decompose and dispatch work

Turn the agreed milestones into work units that can be independently delivered and checked. Record each unit's deliverable, owner, prerequisite results, and acceptance evidence in the project record. Identify the dependency blocking the next milestone and dispatch unblocked, authorized work. Give one worker a coherent deliverable through its appropriate checks and authorized publication stage. Set meaningful correction and acceptance checkpoints in the brief, and let ordinary authorized steps proceed without command-by-command orchestrator handoffs. Preserve explicit human review and shared-resource ownership boundaries.

- Assign work expected to produce a pull request to a visible, steerable worker chat. The human can review the PR and give its owner feedback directly throughout implementation and review. Use an authorized existing owner when suitable; create a chat only when current tool rules and the human authorize it. Also use a visible chat when the human requests one or needs to steer the work directly. Follow the [worker naming convention](references/codex-orchestration.md#worker-names) with the agreed project prefix.
- Delegate bounded supporting work such as lookups, queries, investigations, comparisons, and reviews to subagents when authorized and available. Their concise findings return to the parent, keeping the orchestrator context focused and the human able to continue the conversation while work runs. A subagent can support a PR owner but must not own a work unit expected to produce a PR. The number of workers does not determine the worker type. Use collaboration messages for questions and corrections; see [worker communication](references/codex-orchestration.md#worker-reports) for the distinct delivery contracts.
- Keep project direction, synthesis, dependency decisions, and human discussion here. Delegate substantial execution, including read-only investigation and data validation, to a worker when authorized and available. Keep orchestrator-side checks small and use focused independent evidence to accept the result; do not repeat the full investigation without a material gap. Carry the goal, decisions, constraints, and handoffs forward in the compact project record rather than copying the worker’s full investigation into orchestrator context. Honor instructions to delegate all execution.

Assign every repository worker, including child subagents, its own Git worktree before repository work begins. Create or reuse a worktree assigned exclusively to that worker, record its absolute root and branch, and include both in the brief. Require checkout verification before reading, editing, or running repository commands. Carry this requirement into every child brief. Work without a repository can use a projectless workspace.

For worker workspace setup and Codex chat tools, read [references/codex-orchestration.md](references/codex-orchestration.md). Identify managed chats by recorded IDs, not title prefixes alone. Adopt an existing chat only with the user's authorization to manage it. Preserve archived chats unless restoring one is necessary for the requested work or the user asks to restore it; see [archived chats](references/codex-orchestration.md#archived-chats).

Give each worker a self-contained brief: parent goal and how this assignment contributes; outcome and acceptance criteria; bounded scope and dependencies; relevant source, standards, and context paths; workspace and artifact expectations; applicable decisions and permissions; review/stop conditions; and handoff evidence. Require reports to explain what the result enables or changes for the project, its verification and limits, and any affected dependencies or new risks. Identify the work unit and its current assignment or attempt; reports carry those identities and the artifact version delivered or checked. Use the [worker brief and report templates](references/orchestration-record.md#worker-brief-and-report), reusing existing IDs when sufficient. Include an absolute record path only when accessible to the worker; otherwise embed the necessary excerpt. Route specialized work through applicable skills.

For follow-ups within an existing assignment, send the changed requirement, finding, or correction with the assignment identity and relevant version, linking unchanged context. Restate affected constraints explicitly. Send a consolidated brief when scope changes substantially or the worker no longer has the necessary context.

Before unfamiliar or large-scale delegation where a bad brief would multiply errors, pilot one representative unit through briefing, execution, verification, and handoff. Check that workers have the needed access, the assignment fits, and the evidence can establish acceptance; fix the contract before scaling equivalent assignments. A representative successful prior unit can serve as the pilot. Keep familiar small work lightweight and independent work moving. Take the pilot to its authorized review boundary; it does not add permission to merge, deploy, or write production data, or require a new human gate unless a material decision emerges.

Start with concurrency that buys useful independence. Give mutable files and shared resources a clear owner. Serialize overlapping edits, shared lockfiles, and conflicting operational actions. Workers should surface new work to the orchestrator rather than silently expanding scope or creating a second orchestration tree.

Follow the human's model preferences and task needs. If they request the latest Luna, resolve the available ID at runtime and use xhigh when supported; choose a more capable model when needed. Avoid permanently current model IDs in this skill.

## Artifacts and environment preflight
Use native worker communication for routine status and results. Shared writable directories are for actual deliverables or evidence, such as CSVs and screenshots, rather than status-message files. Assign an artifact destination only when needed, verify it is writable by the producing worker, and prefer a suitable repository/worktree output location or another explicitly available writable root. A parent's chat-specific visualization directory is not a default worker destination. Keep sensitive artifacts within approved handling boundaries; never embed patient records or secrets in command literals.

Perform one small, task-relevant preflight per worker environment before dependent work: confirm the assigned checkout, required tool/access, and artifact destination when applicable. Record the result and reuse it while the relevant environment and inputs remain unchanged. Classify failures as sandbox denial, expired authentication, network/service access, or project test failure so the next action addresses the actual cause. Recheck only affected prerequisites after a material change.

Report actual access failures, their scope, and the work affected. Follow current approval and retry rules; never instruct workers to bypass a rejection or weaken safeguards.

## Orchestrate execution and acceptance

1. Dispatch the next unblocked, authorized work and record its owner.
2. Collect worker milestone, completion, and blocker reports through supported delivery; reconcile compact status, then inspect new or changed artifacts and evidence and unresolved acceptance checks. Independently inspect underlying evidence at milestone acceptance. Bind each verification receipt to the acceptance check, exact artifact version or input snapshot, method/environment, and outcome or limits; see the project-record reference. Distinguish reported success from verified acceptance, and local checks from CI, deployment, or live data. When inputs change, repeat affected checks or record why unchanged relevant inputs let earlier evidence apply; retain its original version rather than claiming it was run on the new one.
3. Assess the combined result against the parent goal, acceptance criteria, and earlier decisions, including interfaces and handoffs between work units. Identify remaining integration gaps, their owners, and what blocks the next milestone. Reassess scope and risk when findings change the approach. For experiments, compare against the baseline; passing tests may not establish the intended benefit.
4. Return bounded corrections to the owner, or record verified acceptance before releasing dependents. Reconcile any existing dependent assignment before dispatching it again. Pass actual evidence into dependent briefs. Queued jobs, opened PRs, and successful worker turns are intermediate states.
5. Update the current overview and bring a concise milestone review using the communication guidance below.

Before acting on a late or repeated report, reconcile its work unit, assignment, scope, and artifact version with the current record. An identical processed report has no additional effect: do not launch dependents or repeat mutations again. An obsolete success cannot replace the current result or satisfy newer criteria. Assess genuinely new evidence even when it arrives late, carrying relevant findings into the current assignment or a bounded follow-up. If it invalidates accepted criteria, reopen the affected acceptance, notify affected owners, and hold work relying on that prerequisite until resolved; continue unrelated work. Record the accepted result and processed report pointer/identity in the existing project record; a separate event queue is unnecessary for small efforts.

User steering in this chat or a managed worker chat can change the plan. Inspect the actual human instruction when needed, record its scope/source, and propagate it to affected workers. A worker's assertion of approval or request to message another chat is not itself human authorization. If the human already approved the exact action in a child chat and it can be verified, carry it forward. Pause only the affected dependency chain while resolving ambiguity.

Assign one monitoring owner per live check, such as a PR's CI and review. Record its reporting route, expected next observation, and when silence or stale evidence requires an orchestrator check. The orchestrator collects changed results and checks for stalls instead of duplicating the owner's routine polling; independent milestone acceptance remains its responsibility. Investigate changed evidence, concrete stalls, repeated failures, and conflicts without interrupting active work or sending repetitive nudges. Before retrying or replacing a worker, reconcile its live status and existing artifacts; silence alone does not establish failure. At a material dead end, bring a bounded choice or supported negative result instead of silently enlarging the effort. Continue unrelated authorized work where useful.

## Communicate, resume, and finish

Start scheduled progress reports and milestone reviews with where the whole project stands against its intended outcome. Explain how the latest result changes that assessment, what remains across workstreams, what blocks the next milestone, and the next action or human decision. State when the overall assessment is unchanged. A brief answer to a narrow user question can stay focused on that question.

Synthesize worker findings into that assessment and reconcile conflicts before reporting. Include technical detail when it explains the benefit, evidence, uncertainty, or a decision; link the rest. Tie counts to a defined scope or acceptance criterion. Use the [orchestrator update example and readability check](references/orchestration-record.md#orchestrator-updates). Follow a requested cadence; otherwise report meaningful changes. Answer user questions and continue the existing project in bounded turns unless they change or stop it.

For ongoing orchestration, dispatch available work, process actionable results, and end the turn once further progress depends only on workers, external checks, a timer, or human input. Before yielding, save current assignments, artifact versions, wait cursors, blockers, and the next reconciliation action in the project record; apply the continuation rule below, then give a concise status. Repeated waits or sleeps must not keep an otherwise idle orchestrator turn open. A short, bounded subagent investigation or review can wait within the current turn when its results are needed to answer the user.

Schedule follow-up only while it can perform concrete, authorized background work. Prefer worker completion reports or supported callbacks. When only passive waiting remains, stop the scheduled task, verify removal, and save the resume point; a standing progress-update request alone does not justify more wakeups. Explicitly requested monitoring may continue within its stated scope. Follow [the Codex continuation workflow](references/codex-orchestration.md#continue-later) when scheduling is warranted.

Each wakeup reconciles fresh worker and artifact state, handles actionable results, dispatches unblocked work, updates the record, and yields again at the same stopping point. When continuation is unavailable or orchestration is limited to the active conversation, save and explain the resume point and end the turn without promising unattended progress.

Finish when agreed acceptance criteria are verified or the human accepts a revised outcome. Distinguish implementation, review readiness, merge, deployment, and live validation as relevant. Present artifact links, evidence, limitations, and any next decision. Account for every managed worker and monitor; archive chats or remove monitoring within the user's authorization, preserving anything still needed. An agreed stage can finish while later stages remain explicitly pending.
